# KMPメモ帳 ハンズオン手順書

この手順書では、Kotlin Multiplatform（KMP）で「KMPメモ帳」を作りながら、1つの Kotlin コードが Android / iOS / Web で動く流れを体験します。

今日のゴールは、KMPを完璧に理解することではありません。まずは「共通コードで作れる部分」と「OSごとに書き分ける部分」の境目を、自分の手で動かしながらつかむことです。

講座中は、細かい構文をすべて暗記しようとしなくて大丈夫です。むしろ大事なのは、「この処理は全OSで同じだから共通に置ける」「この処理はOSのAPIに依存するから書き分ける」という判断の流れです。KMPは魔法のようにすべてを1つにする技術ではなく、共通化できるところを見極めて、違うところだけを小さく分けるための技術です。

今回作る「KMPメモ帳」は、見た目は小さなメモアプリですが、KMPの学びが段階的に入っています。前半では UI とデータ操作を共通コードだけで作り、後半では現在時刻と保存処理を通して `expect / actual` を体験します。

## 0. 全体像

KMPで最初に覚えることは、コードの置き場所で動く環境が決まる、ということです。

```text
shared/src/
├─ commonMain/    全環境で動く共通コード
├─ androidMain/   Android専用コード
├─ iosMain/       iOS専用コード
├─ wasmJsMain/    Web（Wasm）専用コード
└─ jsMain/        Web（JS）専用コード
```

今日の判断はいつも同じです。

「これは `commonMain` に置けるか。置けないなら、どの環境専用のフォルダに置くか。」

たとえば、メモの本文を検索する処理は、Android でも iOS でも Web でも同じ Kotlin の `filter` で書けます。このような処理は `commonMain` に置けます。一方で、Android の `SharedPreferences` や iOS の `NSUserDefaults` のような保存APIは、それぞれのOSにしか存在しません。このような処理は `androidMain` や `iosMain` に置きます。

KMPの設計では、「共通コード」と「専用コード」が混ざらないようにフォルダで分かれています。これにより、共通コードから Android 専用APIをうっかり呼ぶ、といったことが起きにくくなります。置き場所そのものが安全装置になっている、と考えると理解しやすいです。

前半では、メモの追加、削除、検索、お気に入り、件数表示をすべて `commonMain` に書きます。つまり、Android / iOS / Web 向けの書き分けはゼロです。

後半では、現在時刻の取得と保存処理を追加します。ここで OS ごとの API の違いにぶつかるので、`expect / actual` を使って書き分けます。

この講座で触る主なファイルは次の通りです。

```text
shared/src/commonMain/kotlin/org/example/project/Memo.kt
shared/src/commonMain/kotlin/org/example/project/App.kt
shared/src/commonMain/kotlin/org/example/project/MemoStorage.kt
shared/src/commonMain/kotlin/org/example/project/Platform.kt
shared/src/androidMain/kotlin/org/example/project/Platform.android.kt
shared/src/iosMain/kotlin/org/example/project/Platform.ios.kt
shared/src/wasmJsMain/kotlin/org/example/project/Platform.wasmJs.kt
shared/src/jsMain/kotlin/org/example/project/Platform.js.kt
androidApp/src/main/kotlin/org/example/project/MainActivity.kt
```

最初から全部を把握する必要はありません。Step が進むたびに、「今は共通コードを書いているのか」「今は環境ごとの差を書いているのか」を確認しながら進めます。

## 1. 起動確認

まずは Web で起動して、プロジェクトが動く状態か確認します。

```bash
./gradlew :webApp:wasmJsBrowserDevelopmentRun
```

初回は依存関係の取得とビルドで数分かかることがあります。ブラウザで `localhost:8080` が開き、「KMPメモ帳」の画面が表示されれば準備完了です。

### Android で起動する

Android エミュレータ（または USB 接続した実機）を先に起動しておきます。エミュレータは Android Studio の Device Manager から作成・起動できます。

その状態で、次のコマンドでアプリをビルドしてインストールします。

```bash
./gradlew :androidApp:installDebug
```

インストール後、アプリ一覧の「KMPメモ帳」を手でタップして起動します。コマンドから直接起動したい場合は、`adb` が使える環境なら次を実行します。

```bash
adb shell am start -n org.example.project/.MainActivity
```

Android Studio を使う場合は、実行構成で `androidApp` を選び、緑の再生ボタンで実行するのが一番簡単です。CLI ビルドと同じことを IDE がやってくれます。

うまくいかないときは、`adb devices` でエミュレータ／実機が `device` として見えているかを先に確認してください。

### iOS で起動する

iOS は Gradle から直接は起動しません。Xcode（macOS が必要）でシミュレータに乗せます。手順書のプロジェクトには Compose 側を iOS 用に公開する `MainViewController` が用意済みなので、Xcode プロジェクトを開いて実行するだけです。

```bash
open iosApp/iosApp.xcodeproj
```

Xcode が開いたら、上部で任意の iOS シミュレータ（例: iPhone 15）を選び、▶ ボタン（Run）を押します。初回は Kotlin/Native のコンパイルが走るため時間がかかります。

コマンドラインだけで完結させたい場合は、次のようにビルド＆シミュレータ実行もできます（シミュレータ名は環境に合わせて変更してください）。

```bash
xcodebuild -project iosApp/iosApp.xcodeproj \
  -scheme iosApp \
  -destination 'platform=iOS Simulator,name=iPhone 15' \
  build
```

このプロジェクトの iOS ターゲットは `iosArm64`（実機）と `iosSimulatorArm64`（Apple Silicon のシミュレータ）です。Intel Mac のシミュレータ（`iosX64`）は対象に含めていないため、シミュレータ実行は Apple Silicon Mac を前提にしています。

### UI も共通、という確認ポイント

3つの起動方法を試すと分かりますが、Web・Android・iOS はどれも同じ画面が出ます。これは **Compose Multiplatform** によって UI 自体を共通化しているからです。今回は各プラットフォームの「入口」だけが違い、その先はすべて `commonMain` の同じ `App()` を呼んでいます。

```text
Android : MainActivity の setContent { App() }
iOS     : MainViewController() = ComposeUIViewController { App() }
Web     : ComposeViewport { App() }
```

つまり、データモデルやロジックだけでなく、ボタンやリストなどの見た目も 1 つの Kotlin コードで書けています。iOS 側の `ContentView.swift` は、この Compose 製の画面を SwiftUI に貼り込むだけの薄いラッパーです。KMP と一口に言っても「ロジックだけ共通化する」使い方もありますが、今回は Compose Multiplatform を使って UI まで共通化する構成にしています。

この時点では、まだ機能が少なくても問題ありません。ここから全員で機能を足していきます。

ここで先に Web で確認するのは、Android エミュレータや iOS シミュレータより起動が軽く、会場でも確認しやすいからです。KMPの本質は「同じ `shared` のコードが複数ターゲットで使われる」ことなので、最初の動作確認は一番手軽なターゲットで問題ありません。

うまく起動しない場合は、まず次の点を確認してください。

- JDK が入っているか
- Android Studio または IntelliJ で Gradle Sync が通っているか
- すでに別のプロセスが `localhost:8080` を使っていないか
- 初回ビルド中で、まだ完了していないだけではないか

講座では、ここで深追いしすぎないのも大切です。全員がコードを書く時間を確保するため、環境トラブルが長引く場合は隣の人の画面や講師の画面で流れを追えるようにします。

## 2. ハンズオン1: 共通コードだけで作る

前半のテーマは「書き分けゼロで、どこまで作れるか」です。

編集する中心は次のフォルダです。

```text
shared/src/commonMain/kotlin/org/example/project/
```

ここに置いたコードは Android / iOS / Web すべてで使われます。

この前半では、あえて保存や現在時刻のようなOS依存の処理を後回しにします。まずは「普通のアプリ機能の多くは共通化できる」という感覚を作るためです。データを作る、状態を持つ、一覧を表示する、検索する、並び替える。このあたりは OS の機能というよりアプリのロジックなので、Kotlin の共通コードとして扱いやすい領域です。

### Step 1-1. データモデル `Memo` を作る

まず、メモ1件を表すデータの形を作ります。

対象ファイル:

```text
shared/src/commonMain/kotlin/org/example/project/Memo.kt
```

```kotlin
data class Memo(
    val id: Long,
    val text: String,
    val createdAt: String,
    val favorite: Boolean = false,
)
```

`data class` は、データを入れるための箱です。Kotlin が `equals`、`copy`、`toString` などを自動で用意してくれます。

ここで重要なのは、この `Memo` が `commonMain` にあることです。つまり、この1つの定義を Android / iOS / Web がそのまま使います。iOS 用に Swift のモデルを書き直す必要はありません。

`id` は、一覧の中で「どのメモか」を識別するために使います。削除やお気に入り更新では、この `id` が目印になります。

`favorite` はお気に入りフラグです。`false` のデフォルト値を付けておくと、あとから項目を足しても既存のコードを壊しにくくなります。

ここではまだ、`Memo` は単なるデータの定義です。画面に出す処理も、保存する処理も、このファイルには書きません。データの形を小さく独立させておくと、あとから検索、並び替え、保存のどの処理からも同じ `Memo` を使えます。

`createdAt` はこの時点では空文字でも構いません。後半で `nowFormatted()` を追加したときに、現在時刻が入るようにします。最初から完成形を全部書くのではなく、Step が進むにつれてフィールドの意味が育っていく構成にしています。

講師補足:

- `data class` は「値」を表すのに向いています
- `id` は画面表示のためだけでなく、更新対象を探すためにも使います
- `favorite` のようなフラグを足しても、モデルが共通なら全プラットフォームで同じように扱えます

確認ポイント:

- コンパイルが通る
- まだ画面の見た目は大きく変わらなくてよい

### Step 1-2. 画面の状態を持つ

次に、入力中の文字、メモ一覧、次に使う ID を画面の状態として持ちます。

対象ファイル:

```text
shared/src/commonMain/kotlin/org/example/project/App.kt
```

`App()` の中で、次のような状態を用意します。

```kotlin
var input by remember { mutableStateOf("") }
var memos by remember { mutableStateOf(listOf<Memo>()) }
var nextId by remember { mutableStateOf(0L) }
```

`mutableStateOf` は、Compose が変化を監視できる箱です。この値が変わると、Compose が画面を自動で描き直します。Flutter を知っている人向けに言うと、`setState` に近い役割です。

`remember` は、再描画されても値を保持するための仕組みです。これがないと、画面が描き直されるたびに入力内容やメモ一覧が初期化されてしまいます。

`by` は、状態の箱を毎回 `.value` で開けなくても、普通の変数のように読み書きできるようにする書き方です。

Compose では、画面は「状態から作られるもの」と考えます。入力欄に何が入っているか、メモが何件あるか、検索キーワードが何か。これらの状態が変わるたびに、Compose が必要な部分を描き直します。

ここで大事なのは、画面の部品を直接いじるのではなく、状態を変えることです。たとえば「メモを1件追加する」という操作は、リストUIに行を直接追加するのではなく、`memos` という状態を新しいリストに更新します。その結果として、画面が再描画されます。

追加ボタンでは、入力が空でないときだけ新しいメモを作ります。

```kotlin
if (input.isNotBlank()) {
    memos = memos + Memo(
        id = nextId,
        text = input.trim(),
        createdAt = ""
    )
    nextId++
    input = ""
}
```

ポイントは、`memos` に直接追加するのではなく、`memos + Memo(...)` で新しいリストを作って代入していることです。Compose は「別のリストが代入された」と検知して、画面を再描画します。

`nextId` を `memos.size` で代用しない理由も大切です。メモを削除すると `size` は減るため、同じ ID が再利用される可能性があります。ID は一覧の行を安定して識別するためのものなので、削除しても戻らない連番として持ちます。

`input.trim()` を使っているのは、前後の余分な空白を取り除くためです。一方で、`isNotBlank()` でチェックしているので、スペースだけのメモは追加されません。小さな処理ですが、こうした入力の扱いも全OSで同じにできます。

この段階では `createdAt = ""` で構いません。現在時刻は OS ごとのAPIが必要になるため、後半まで空けておきます。ここで無理に時刻処理まで入れないことで、「共通化できる部分」と「共通化できない部分」の境目が見えやすくなります。

よくあるつまずき:

- `memos + Memo(...)` の結果を `memos` に代入し忘れると、画面は変わりません
- `nextId++` を忘れると、複数のメモが同じ ID になり、削除や更新で分かりにくい挙動になります
- `remember` を付け忘れると、再描画時に状態が初期化されることがあります

確認ポイント:

- 入力欄に文字を入れて「追加」を押すとメモが増える
- 空白だけでは追加されない
- 追加後、入力欄が空になる

### Step 1-3. 一覧表示と削除

メモ一覧は `LazyColumn` で表示します。

```kotlin
LazyColumn {
    items(memos, key = { it.id }) { memo ->
        Card {
            Text(memo.text)
        }
    }
}
```

`LazyColumn` は、縦方向のリストを効率よく表示する Compose の部品です。見えている範囲を中心に描画するため、件数が増えても扱いやすくなります。Flutter の `ListView.builder` に近いものです。

`key = { it.id }` は、各行を一意に識別するために指定します。削除や並び替えが入る画面では、どの行がどのデータに対応しているかを安定させるために重要です。

`key` は、最初は地味に見える指定ですが、リストUIではとても重要です。Compose は再描画のときに「前回のどの行が、今回のどの行に対応するのか」を判断します。その手がかりが `key` です。

もし `key` がない状態で削除や並び替えをすると、行の状態やアニメーションが意図しないデータに結びつくことがあります。今回のように `id` を持たせておくと、メモ本文が同じでも別の行として扱えます。

削除は、本文部分をタップしたときに行います。

```kotlin
Modifier.clickable {
    memos = memos - memo
}
```

ここでも、元のリストを直接変更するのではなく、「そのメモを除いた新しいリスト」を作って `memos` に代入しています。

本文をタップすると削除されるUIは、実務アプリとしては少し大胆です。本来なら削除ボタンや確認ダイアログを用意することも多いですが、講座では「リストから1件取り除く処理」を最短で体験するために、この形にしています。

削除処理そのものは `memos = memos - memo` の1行です。このシンプルさが Kotlin のコレクション操作の良さであり、KMPで共通化しやすい部分でもあります。

講師補足:

- UIの見た目は Compose Multiplatform が共通化しています
- リスト操作は Kotlin の標準的な処理です
- ここまでまだ Android / iOS / Web の専用コードは出てきません

確認ポイント:

- 追加したメモが一覧に出る
- メモをタップすると削除される

### Step 1-4. 検索を付ける

次に、検索キーワードを状態として持ちます。

```kotlin
var query by remember { mutableStateOf("") }
```

検索欄に入力された文字で、表示するメモだけを絞り込みます。

```kotlin
val visibleMemos = memos
    .filter { query.isBlank() || it.text.contains(query, ignoreCase = true) }
```

ここで大事なのは、元データの `memos` を壊さないことです。`memos` はすべてのメモを持つ本体として残し、画面に出すための `visibleMemos` を別に作ります。

検索欄が空なら全件表示します。検索欄に文字が入っていれば、その文字を含むメモだけを表示します。

そして、この `filter` はただの Kotlin の処理です。つまり、Android 用、iOS 用、Web 用に検索処理を書き分ける必要がありません。`commonMain` に1回書くだけで、すべての環境に検索が効きます。

この Step は、前半の中でも特に KMP らしさが分かりやすいところです。検索はアプリとしてはよくある機能ですが、OS 固有のAPIを使っていません。文字列に対して `contains` し、リストに対して `filter` しているだけです。

つまり、検索処理は「Android の検索」でも「iOS の検索」でもなく、「アプリのルール」です。このようなアプリ独自のルールは、KMPで共通化しやすい代表例です。

`ignoreCase = true` を指定しているため、大文字と小文字を区別せずに検索します。日本語の検索では違いが分かりにくいですが、英数字を入れて試すと挙動を確認しやすいです。

ここで `visibleMemos` という表示用の変数を作っている点も重要です。検索するたびに元の `memos` を削ってしまうと、検索欄を空にしたときに元に戻せません。元データを保持し、表示用データを別に作るのは、UI実装でよく使う考え方です。

確認ポイント:

- 検索欄に文字を入れると、一致するメモだけが残る
- 検索欄を空に戻すと全件表示に戻る

### Step 1-5. お気に入り、件数、並び替え

最後に、共通コードだけで少し実用的な機能まで作ります。

表示用のリストを、検索後に並び替えます。

```kotlin
val visibleMemos = memos
    .filter { query.isBlank() || it.text.contains(query, ignoreCase = true) }
    .sortedWith(
        compareByDescending<Memo> { it.favorite }
            .thenByDescending { it.id }
    )
```

この並び順は、次の2段階です。

- お気に入りのメモを上に出す
- 同じお気に入り状態の中では、新しいメモを上に出す

お気に入りの切り替えは、該当する1件だけを更新した新しいリストを作ります。

```kotlin
memos = memos.map {
    if (it.id == memo.id) it.copy(favorite = !it.favorite)
    else it
}
```

`map` で全件を見ながら、ID が一致したメモだけ `copy` で変更します。`data class` の `copy` は「一部の値だけ変えたコピー」を作れるので、このような更新に向いています。

ここでは「リストの中の1件を更新する」処理を体験しています。ミュータブルなリストを直接書き換えるのではなく、`map` で新しいリストを作るのがポイントです。

`if (it.id == memo.id)` で対象のメモを探し、対象だけ `favorite` を反転します。それ以外のメモはそのまま返します。結果として、同じ件数の新しいリストができます。

この書き方は少し遠回りに見えるかもしれません。しかし、状態を新しい値として差し替える形にしておくと、Compose が変化を検知しやすくなり、処理の見通しも良くなります。

件数表示は、タイトルの右側などに出します。

```kotlin
Text("${memos.size}件")
```

ここまでで、メモの追加、削除、検索、お気に入り、並び替え、件数表示まで作れました。しかも、すべて `commonMain` だけです。

これが「共通化できる部分」です。

ここで一度、手を止めて整理します。いま作った機能は、実用的なメモアプリに近い機能です。それでも、まだOS専用コードは書いていません。これは、UIとアプリロジックの多くが「OSの違い」ではなく「アプリの仕様」だからです。

KMPを導入するときは、いきなりすべてを共通化しようとするよりも、まずこのようなアプリロジックを共通化するところから考えると現実的です。検索、並び替え、入力チェック、データ変換、業務ルールなどは、共通化の候補になりやすいです。

前半のまとめ:

- `Memo` は共通のデータモデル
- `App.kt` の UI と状態管理も共通
- 検索や並び替えは Kotlin の処理なので共通
- ここまで Android / iOS / Web の書き分けはゼロ

確認ポイント:

- ☆を押すと★に変わる
- ★のメモが上に移動する
- 新しいメモほど上に表示される
- 件数が正しく表示される

## 3. ハンズオン2: 共通化できない部分を書き分ける

後半のテーマは「共通化できない壁を `expect / actual` で越える」です。

前半はすべて `commonMain` に書けました。しかし、現在時刻の取得や保存先の API は OS ごとに違います。

Android なら `SimpleDateFormat` や `SharedPreferences`、iOS なら `NSDateFormatter` や `NSUserDefaults`、Web なら JavaScript の `Date` や `localStorage` を使います。

このように、共通コードに直接書けない処理を扱うために `expect / actual` を使います。

ここでのポイントは、「共通化できないものが出てきたからKMPが失敗した」というわけではないことです。むしろ KMP は、違うところを違うものとして安全に扱うための仕組みを持っています。それが `expect / actual` です。

`expect / actual` は、共通コード側に「こういう関数があるはず」と宣言し、各プラットフォーム側で「この環境ではこう実装する」と答える仕組みです。共通コードは `expect` の名前だけを見て呼び出し、実際の中身はビルド対象に応じて差し込まれます。

今回の後半では、あえて少し面倒な体験もします。同じ `nowFormatted()` を Android / iOS / Web それぞれに書くのは手間です。しかし、この手間を体験することで、KMPで何が共通化できて、何が書き分けになるのかがはっきり見えます。

### Step 2-1. `expect` で約束を書く

対象ファイル:

```text
shared/src/commonMain/kotlin/org/example/project/Platform.kt
```

`commonMain` には、中身を書かずに「各OSがこの関数を用意する」という約束だけを書きます。

```kotlin
expect fun nowFormatted(): String
expect fun saveMemos(data: String)
expect fun loadMemos(): String
```

`expect` は、共通コード側の宣言です。ここには実装を書きません。

この時点で、各ターゲットに対応する `actual` がまだ無ければコンパイルエラーになります。これは失敗ではなく、KMPの安全装置です。

「全環境分の実装が揃っていないのでビルドできません」とコンパイラが教えてくれます。

ここで一度、わざとエラーを見るのがおすすめです。KMPでは、共通コードに `expect` を書いた瞬間に、すべての対象ターゲットで対応する `actual` が必要になります。今回のプロジェクトには Android、iOS、wasmJs、js があるので、それぞれに実装が必要です。

この制約は少し厳しく感じるかもしれませんが、実務では実装漏れを防ぐ助けになります。たとえば Android だけ実装して iOS を忘れていた場合、後からiOSビルドで初めて壊れるのではなく、コンパイル時に気づけます。

`expect` に書く関数の形は、共通コードから見たい最小の形にするのがコツです。今回なら、共通コードは「現在時刻を文字列でほしい」「文字列を保存したい」「文字列を読み込みたい」だけを知っていれば十分です。Android の `Context` や iOS の `NSUserDefaults` を、共通コードに見せる必要はありません。

確認ポイント:

- `actual` が無い状態ではエラーになる
- エラーになる理由が「各環境の実装がまだ無いから」だと説明できる

### Step 2-2. 現在時刻の `actual` を書く

まず、追加したメモに時刻を表示します。

Android:

```text
shared/src/androidMain/kotlin/org/example/project/Platform.android.kt
```

```kotlin
actual fun nowFormatted(): String =
    SimpleDateFormat("HH:mm", Locale.getDefault()).format(Date())
```

iOS:

```text
shared/src/iosMain/kotlin/org/example/project/Platform.ios.kt
```

```kotlin
actual fun nowFormatted(): String {
    val formatter = NSDateFormatter()
    formatter.dateFormat = "HH:mm"
    return formatter.stringFromDate(NSDate())
}
```

Web（Wasm）:

```text
shared/src/wasmJsMain/kotlin/org/example/project/Platform.wasmJs.kt
```

```kotlin
actual fun nowFormatted(): String = jsNowString()

@OptIn(kotlin.js.ExperimentalWasmJsInterop::class)
private fun jsNowString(): String = js("new Date().toTimeString().slice(0,5)")
```

Web（JS）:

```text
shared/src/jsMain/kotlin/org/example/project/Platform.js.kt
```

```kotlin
actual fun nowFormatted(): String =
    js("new Date().toTimeString().slice(0,5)")
```

ここで体験してほしいポイントは、同じ「現在時刻を `HH:mm` で返す」という処理でも、実装は環境ごとに違うことです。

一方で、`App.kt` から見ると呼び出しは1つだけです。

```kotlin
createdAt = nowFormatted()
```

共通コードは `nowFormatted()` を呼ぶだけで、実際にどの API が使われるかはビルド対象の環境によって切り替わります。

特に iOS では、Kotlin から `NSDateFormatter` のような Foundation API を直接呼んでいます。Flutter の Platform Channel のような橋を自分で用意する必要はありません。

Android の実装では `SimpleDateFormat` を使っています。最近の Android では `java.time` を使う選択肢もありますが、対応APIレベルの都合で使える範囲が変わることがあります。講座では分かりやすく、従来から使われている `SimpleDateFormat` を使っています。

iOS の実装では `platform.Foundation` のクラスを Kotlin から呼びます。ここは初めて見ると少し不思議に感じるかもしれません。KMPでは Kotlin/Native を通して iOS のネイティブAPIにアクセスできるため、Kotlin のファイル内に `NSDateFormatter` が出てきます。

Web の実装では JavaScript の `Date` を呼びます。`wasmJsMain` と `jsMain` はどちらも Web 向けですが、Kotlin のターゲットとしては別なので、それぞれに `actual` が必要です。同じようなコードを2回書くのは少し面倒ですが、「ターゲットが別なら actual も別」というルールを体験するには良い題材です。

この Step の見どころは、`App.kt` 側が何も変わらないことです。共通UIはただ `nowFormatted()` を呼ぶだけです。その裏側で、Android なら Android の時刻API、iOS なら iOS の時刻API、Web ならブラウザのAPIが動きます。

確認ポイント:

- 追加したメモに `14:32` のような時刻が表示される
- `actual` が1つでも欠けるとビルドできないことを理解する

### Step 2-3. 永続化の変換処理を共通に寄せる

次は「閉じても消えないメモ」にします。

保存先は OS ごとに違いますが、保存するデータの変換は共通化できます。

対象ファイル:

```text
shared/src/commonMain/kotlin/org/example/project/MemoStorage.kt
```

ここでは、メモ一覧と文字列の相互変換を行います。

```kotlin
fun encodeMemos(memos: List<Memo>): String
fun decodeMemos(data: String): List<Memo>
```

保存 API は、多くの場合「1本の文字列」を保存する形で扱えます。そこで、`List<Memo>` を文字列に変換する処理は `commonMain` に置きます。

設計の考え方は次の通りです。

- `List<Memo> ⇄ String` の変換は全環境で同じなので共通化する
- 実際にどこへ保存するかは OS ごとに違うので `expect / actual` にする

このプロジェクトでは、学習用に「1メモ = 1行」「フィールドはタブ区切り」という手書きの変換を使っています。メモ本文にタブや改行が入っても壊れないよう、保存前にエスケープし、読み込み時に戻します。

実務では、このような手書き変換ではなく `kotlinx.serialization` を使うことが一般的です。今回は依存を増やさず、KMP の構造を見やすくするために手書きにしています。

この Step で伝えたいのは、「保存」という機能の中にも共通化できる部分とできない部分がある、ということです。

保存先は OS ごとに違います。Android は `SharedPreferences`、iOS は `NSUserDefaults`、Web は `localStorage` です。しかし、「メモ一覧をどういう文字列にするか」は OS に依存しません。だから、その変換処理は `MemoStorage.kt` として共通に置けます。

このように、大きな機能をそのまま「共通化できる / できない」で判断するより、中身を分解して考えるのが大切です。保存機能全体はOS差分を含みますが、データ変換だけなら共通化できます。

今回のエンコード形式は学習用です。1行に1メモを置き、ID、お気に入り、作成時刻、本文をタブ区切りで並べます。本文にタブや改行が入った場合に壊れないよう、`\t` や `\n` のように逃がして保存します。

講師補足:

- 「保存先」は書き分ける
- 「保存する形への変換」は共通化する
- 実務では JSON 化や `kotlinx.serialization` を使うことが多い
- この分解の考え方は、通信やDBでも同じように使える

確認ポイント:

- 変換処理は `commonMain` に置けると説明できる
- 保存先そのものは `commonMain` に置けないと説明できる

### Step 2-4. 保存先の `actual` を書く

保存先は環境ごとに違うので、それぞれの `actual` を書きます。

Android では `SharedPreferences` を使います。

```kotlin
lateinit var androidContext: Context

private val prefs
    get() = androidContext.getSharedPreferences(PREF_NAME, Context.MODE_PRIVATE)

actual fun saveMemos(data: String) {
    prefs.edit().putString(PREF_KEY, data).apply()
}

actual fun loadMemos(): String =
    prefs.getString(PREF_KEY, "") ?: ""
```

Android だけは、少し一手間があります。`SharedPreferences` を使うには `Context` が必要ですが、`Context` は Android 専用のものなので、共通コードから直接触れません。

そこで、Android アプリ側の `MainActivity` から起動時に渡します。

対象ファイル:

```text
androidApp/src/main/kotlin/org/example/project/MainActivity.kt
```

```kotlin
androidContext = applicationContext
```

iOS では `NSUserDefaults` に保存します。

```kotlin
actual fun saveMemos(data: String) {
    NSUserDefaults.standardUserDefaults.setObject(data, KEY)
}

actual fun loadMemos(): String =
    NSUserDefaults.standardUserDefaults.stringForKey(KEY) ?: ""
```

Web では `localStorage` に保存します。

```kotlin
actual fun saveMemos(data: String) {
    js("localStorage.setItem('memos', data)")
}

actual fun loadMemos(): String =
    js("localStorage.getItem('memos') || ''")
```

ここで大切なのは、OSごとの差が完全に対称ではないことです。iOS と Web は保存 API をその場で呼べますが、Android は `Context` の受け皿が必要です。

この非対称さが、KMP導入時の現実的なコストです。実務では DI やライブラリを使って隠すことが多いですが、内部ではこのような差を扱っています。

Android の `lateinit var androidContext: Context` は、講座用の分かりやすい実装です。`SharedPreferences` を取得するには `Context` が必要ですが、`shared` の共通コードから Android の `Activity` や `Application` を直接知るべきではありません。そこで、Android 側の起動処理で `applicationContext` を渡しています。

この設計は「Androidだけ一手間かかる」例として重要です。KMPを使うと、すべてのプラットフォームが完全に同じ形で扱えるわけではありません。むしろ、こうした違いをどこに閉じ込めるかが設計のポイントになります。

iOS の `NSUserDefaults` と Web の `localStorage` は、今回の用途では比較的そのまま呼びやすいAPIです。そのため Android より短いコードで済みます。この差は、KMPが悪いというより、各プラットフォームのAPI設計が違うことから来ています。

実務では、今回のようにグローバルな `androidContext` を直接持つ代わりに、DI（Dependency Injection）や `multiplatform-settings` のようなKMP対応ライブラリを使って隠すことがあります。ただ、最初の講座ではあえて素朴に書くことで、どこにOS差分があるのかを見えるようにしています。

確認ポイント:

- Android は `Context` を渡さないと保存 API が使えない
- iOS / Web はそれぞれの保存 API を Kotlin から直接呼べる
- `saveMemos` / `loadMemos` の名前は共通だが、中身は環境ごとに違う

### Step 2-5. 起動時ロードと自動保存をつなぐ

最後に、`App.kt` で保存と復元を画面に接続します。

起動時には、保存済みの文字列を読み込んで `List<Memo>` に戻します。

```kotlin
var memos by remember {
    mutableStateOf(decodeMemos(loadMemos()))
}
```

メモ一覧が変わったら、自動で保存します。

```kotlin
LaunchedEffect(memos) {
    saveMemos(encodeMemos(memos))
}
```

`LaunchedEffect(memos)` は、`memos` が変わるたびに中の処理を実行します。追加、削除、お気に入り変更のたびに保存されるので、保存ボタンを用意しなくても保存漏れが起きにくくなります。

復元後の ID 衝突を避けるため、`nextId` は保存済みメモの最大 ID の次から始めます。

```kotlin
var nextId by remember {
    mutableStateOf((memos.maxOfOrNull { it.id } ?: -1L) + 1L)
}
```

これで、リロードや再起動をしてもメモが残るようになります。

この Step が後半のクライマックスです。これまで別々に作ってきた部品が、ここでつながります。

起動時には `loadMemos()` で保存済みの文字列を取り出し、`decodeMemos()` で `List<Memo>` に戻します。アプリの操作中に `memos` が変わると、今度は `encodeMemos()` で文字列にし、`saveMemos()` で保存します。

流れを分解すると、次のようになります。

```text
起動時:
保存先 → loadMemos() → String → decodeMemos() → List<Memo> → 画面

変更時:
画面操作 → List<Memo> → encodeMemos() → String → saveMemos() → 保存先
```

この中で、`encodeMemos()` と `decodeMemos()` は共通コードです。一方、`saveMemos()` と `loadMemos()` の中身は OS ごとに違います。ここまで来ると、共通化と書き分けの境目がかなり具体的に見えてきます。

`LaunchedEffect(memos)` は、`memos` が変わるたびに保存処理を走らせるための仕組みです。保存処理を追加ボタン、削除処理、お気に入り処理のそれぞれに書くこともできますが、それだと保存し忘れが起きやすくなります。状態の変更を1か所で監視して保存することで、処理をまとめています。

ただし、実務では保存のタイミングや頻度も考える必要があります。大きなデータを毎回保存すると重くなることがありますし、通信を伴う保存ならエラー処理も必要です。今回はローカルの小さなメモなので、変更のたびに保存するシンプルな形にしています。

確認ポイント:

- Web でメモを追加する
- ブラウザをリロードする
- 追加したメモが残っている
- 削除やお気に入り変更もリロード後に反映される

## 4. 今日書いたコードの整理

今日のコードは、3つの層に分けて考えられます。

```text
完全に共通化できるもの
  データモデル、UI、検索、並び替え、件数表示
  → commonMain

ライブラリ次第で共通化できるもの
  日時、保存、通信、DB など
  → KMP対応ライブラリを使うと commonMain に寄せられる場合がある

共通化できないもの
  各OS固有のAPIやライフサイクル
  → expect / actual
```

KMPでは、すべてを無理に共通化する必要はありません。

大切なのは、共通化できるところは `commonMain` に寄せ、共通化できないところだけを小さく `actual` に閉じ込めることです。

今日の「KMPメモ帳」でいうと、データモデル、UI、検索、並び替え、保存用の文字列変換は共通化できました。一方、現在時刻の取得と保存先へのアクセスは書き分けました。

この境目は、プロジェクトや使うライブラリによって変わります。たとえば、日時処理に `kotlinx-datetime` を使えば、今回 `actual` で書いた一部の処理を共通化できるかもしれません。設定保存に `multiplatform-settings` を使えば、保存先の差分もライブラリの中に隠せるかもしれません。

つまり、共通化できる範囲は「自分の頑張り」だけではなく、「KMP対応ライブラリがあるか」「既存の設計と合うか」にも左右されます。KMP導入を考えるときは、言語機能だけでなくエコシステムも一緒に見る必要があります。

実務での考え方:

- まずはドメインロジックやデータ変換など、OSに依存しない処理から共通化する
- UI共有はチームのスキルやプロダクト方針に合わせて判断する
- OS固有APIは小さな `actual` やライブラリの裏側に閉じ込める
- 無理に全部を共通化しようとしない

## 5. 講座中の進め方メモ

講師側は、各ステップで次の順番を意識すると進めやすくなります。

1. まず「どこに書くか」を確認する
2. 次に「なぜそこに置けるのか、または置けないのか」を説明する
3. コードを書く
4. すぐ動作確認する
5. うまく動いたら、Android / iOS / Web のどこまで同じコードで動いているかを確認する

特に強調したいポイントは、次の3つです。

- 前半は `commonMain` だけで実用的な機能まで作れる
- 後半は `expect / actual` によって OS ごとの差を明示的に扱える
- KMP は「全部共有する技術」ではなく「共有できるところを共有し、違うところは小さく書き分ける技術」

受講者に問いかけるとよい質問:

- この処理はOSのAPIを使っていますか
- この処理は Kotlin の標準機能だけで書けますか
- このファイルを `commonMain` に置いたら、iOS や Web でも意味が通りますか
- もし `actual` が必要だとしたら、共通コード側に見せる関数名はどこまで小さくできますか

講座中は、コードを写す時間と説明を聞く時間が混ざりやすいです。各 Step の冒頭では「今からどのファイルを触るか」を先に言い、最後に「この Step で KMP 的に何を学んだか」を一言でまとめると、流れを追いやすくなります。

Step ごとの一言まとめ:

- Step 1-1: データモデルは共通化しやすい
- Step 1-2: 状態が変わるとUIが描き直される
- Step 1-3: リスト操作も共通の Kotlin で書ける
- Step 1-4: 検索はアプリロジックなので共通化できる
- Step 1-5: 更新や並び替えも共通コードで完結する
- Step 2-1: `expect` は共通コード側の約束
- Step 2-2: `actual` は各OSでの答え
- Step 2-3: 保存機能の中でも、変換処理は共通化できる
- Step 2-4: 保存先はOSごとに違う
- Step 2-5: 共通コードと専用コードをつないで完成する

## 付録A. KMPプロジェクトの雛形を自分で作る

今回のハンズオンは用意済みのリポジトリを使いましたが、ゼロから新しい KMP プロジェクトを作る流れも知っておくと、講座後に自分のアプリを始めやすくなります。今のプロジェクト構成（`shared` / `androidApp` / `webApp` / `iosApp`）も、基本はこの雛形生成をベースにしています。

雛形の作り方は主に2つあります。手軽なのは Web ウィザードです。

### 方法1: Web ウィザード（おすすめ）

JetBrains が公式に用意している KMP ウィザードを使います。

1. ブラウザで <https://kmp.jetbrains.com/> を開く
2. プロジェクト名とパッケージ名（今回でいう `org.example.project` のようなもの）を入力する
3. 対象プラットフォームを選ぶ（Android / iOS / Web / Desktop / Server から必要なものだけ）
4. UI を共通化したい場合は「Share UI (Compose Multiplatform)」を有効にする ← 今回のプロジェクトはこれを有効にした構成です
5. 「Download」で ZIP を落として解凍し、Android Studio か IntelliJ IDEA で開く

解凍後に生成されるフォルダは、今回のプロジェクトとほぼ同じ考え方で並んでいます。

```text
shared/ (または composeApp/)   共通コード。commonMain / androidMain / iosMain などを含む
androidApp/                    Android アプリの入口（MainActivity）
iosApp/                        Xcode プロジェクト（SwiftUI から Compose を呼ぶ）
webApp/                        Web（Wasm/JS）の入口
gradle/libs.versions.toml      Kotlin や Compose のバージョンを一元管理
```

ウィザードで作った直後の状態が、ちょうど本手順書の `handson/start` に近い「最小限の画面だけがある状態」です。ここから `commonMain` に機能を足していく流れは、今日やったことと同じです。

### 方法2: Android Studio / IntelliJ のテンプレート

IDE のプラグインからも作成できます。

1. Android Studio に「Kotlin Multiplatform」プラグインを入れる（IntelliJ IDEA Ultimate には同等機能が同梱）
2. 「New Project」→「Kotlin Multiplatform」系のテンプレートを選ぶ
3. 対象プラットフォームと UI 共通化の有無を選んで生成

生成される中身は Web ウィザードとほぼ同じです。IDE 内で完結させたい場合はこちらが便利です。

### バージョンについての注意

KMP と Compose Multiplatform は更新が速く、生成される雛形の Gradle 設定は時期によって変わります。今回のプロジェクトが使っている主なバージョンは次の通りです（`gradle/libs.versions.toml` で管理）。

```text
Kotlin              2.4.10
Compose Multiplatform 1.11.1
Android Gradle Plugin 9.0.1
compileSdk / targetSdk 36 / minSdk 24
```

新しく雛形を作ると、これより新しいバージョンになっていることがよくあります。手順書のコードをそのまま貼っても、`expect / actual` の書き方や Web ターゲットの設定（`wasmJs` まわり）が少し違う場合があるので、ビルドエラーが出たらまず「生成された雛形のバージョンでの書き方」を優先してください。

### 雛形を作ったあと最初に確認すること

自分で雛形を作ったら、今日と同じく、まず一番軽い Web で起動確認するのがおすすめです。

```bash
./gradlew :webApp:wasmJsBrowserDevelopmentRun
```

（モジュール名はウィザードの生成結果によって `:composeApp:` などに変わることがあります。`./gradlew tasks` や `settings.gradle.kts` の `include(...)` で実際のモジュール名を確認してください。）

ここまで動けば、あとは本手順書の Step 1-1 からと同じ流れで、`commonMain` に機能を足していけます。
